# MCP 101 — Model Context Protocol, from zero

> A quick, standalone primer. For the deep dive tied to this repo's actual servers (auth, SSRF guards, stateless design, hands-on curl/Inspector exercises), see `guides/04-mcp.md` (in the agentic-ai course).

## The problem it solves

Every time you give an LLM a "tool" (search the web, read a file, send an email), someone has to write the glue code: describe the tool in JSON Schema, run it when the model asks, and feed the result back. Do that for ten tools across three different apps (a chat UI, an IDE assistant, a CLI agent) and you've written the same plumbing three times, in three incompatible ways.

**MCP (Model Context Protocol)**, introduced by Anthropic in late 2024, is an open standard that moves tools out of the app and into independent **servers** that *any* MCP-aware app can connect to. Build a "GitHub" server once; Claude Desktop, VS Code, Cursor and your own app can all use it unchanged. People call it "USB-C for AI tools" — one plug, many devices.

## Three roles

| Role | What it is | Example |
|---|---|---|
| **Host** | The AI application the user talks to. Owns the model and the conversation. | A chat app, Claude Desktop, an IDE |
| **Client** | A connection object *inside* the host, one per server, speaking the protocol. | The MCP client built into the host's SDK |
| **Server** | A standalone program exposing capabilities over MCP. | A "notes" server, a "GitHub" server, a "database" server |

```
Host (your app)
 ├── client ──► MCP server A  (e.g. notes)
 └── client ──► MCP server B  (e.g. web search)
```

The model itself never talks to a server directly — it only ever sees "tools" the host hands it. The host is the one that speaks MCP.

## The wire format: JSON-RPC 2.0

Every message is plain JSON-RPC 2.0:

```json
// request
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "city": "Chennai" } } }

// response (same id)
{ "jsonrpc": "2.0", "id": 1,
  "result": { "content": [ { "type": "text", "text": "32°C, humid" } ] } }
```

A message with no `id` is a **notification** — fire-and-forget, no reply expected.

## The three primitives

| Primitive | Who decides to use it | Think of it as |
|---|---|---|
| **Tools** | The **model** | An action with a name, a description, and a JSON Schema for its arguments — like a function the model can call |
| **Resources** | The **app / user** | Read-only data behind a URI (`notes://all`, `file:///README.md`) — the host decides what to attach |
| **Prompts** | The **user** | A reusable prompt template with arguments, often surfaced as a slash command |

In practice, almost everything you'll build or use today is a **tool**. A tool is defined by three things the model actually sees:

```ts
{
  name: "delete_note",
  description: "Delete a note by id. Only call this when the user explicitly asks to delete.",
  inputSchema: { id: "string" } // JSON Schema
}
```

> **Key insight:** the name + description + schema *is* the prompt. The model decides whether and how to call a tool purely from that text. Vague descriptions → the model never calls the tool, or calls the wrong one.

## How a turn actually works

1. **Connect & discover.** The client calls `initialize`, then `tools/list` to learn what the server offers. The host turns each tool into a normal function-calling entry for the model.
2. **The model decides.** Given the user's message and the list of available tools, the model may respond with "call `delete_note` with `{id: "42"}`" instead of plain text.
3. **The host executes.** The host's MCP client sends `tools/call` to the right server and gets back a result (or an error).
4. **The model sees the result** and continues the conversation — possibly calling another tool, possibly answering the user.

The server never talks to the model; the host always sits in the middle.

## Transports: how the bytes move

- **stdio** — the host *launches* the server as a child process and talks over stdin/stdout. Simple, local-only (desktop apps, IDEs). Can't be a separately deployed service.
- **Streamable HTTP** — the server is a normal web service with one endpoint (commonly `POST /mcp`). The client POSTs JSON-RPC; the server replies with plain JSON or a short Server-Sent-Events stream. This is what you want when a server needs to run as its own deployable, scalable process (e.g. in a container on Azure).
- **HTTP+SSE (legacy, 2024)** — the original two-endpoint HTTP transport, now superseded by Streamable HTTP. You'll still see it referenced in older tutorials.

## A minimal server (TypeScript)

```ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod";

const server = new McpServer({ name: "demo", version: "1.0.0" });

server.registerTool(
  "add",
  {
    title: "Add two numbers",
    description: "Add two numbers and return the sum.",
    inputSchema: { a: z.number(), b: z.number() },
  },
  async ({ a, b }) => ({
    content: [{ type: "text", text: String(a + b) }],
  }),
);
```

`inputSchema` is a zod shape — the SDK turns it into JSON Schema for discovery *and* validates incoming arguments before your handler runs.

## Why MCP over "just write a function"

- **Reuse across hosts.** One server, many clients — a chat app, an IDE, a CLI agent all connect the same way.
- **Process isolation.** A server can run anywhere (another machine, another language, a sandboxed container) — the host only needs network access.
- **A shared discovery format.** `tools/list` is the same shape regardless of what the server is written in.

## Security basics (don't skip this)

- **Tool output is untrusted input.** Anything a tool returns (a web page, a file, a database row) goes straight into the model's context. Treat it like user input that could contain "ignore previous instructions…".
- **Least privilege.** Don't expose `delete_everything` if `delete_one_item` will do. Use annotations like `destructiveHint` so hosts can require confirmation.
- **Only connect servers you trust.** A malicious server can lie in its tool descriptions ("tool poisoning") to steer the model.

## Try it yourself

```bash
npx @modelcontextprotocol/inspector
```

The Inspector is a browser UI for connecting to any MCP server (stdio or HTTP), listing its tools/resources/prompts, calling them by hand, and watching the raw JSON-RPC messages fly past. It's the fastest way to build intuition before writing any code.

## Check your understanding

1. Who decides when a tool is called — the host, the client, or the model?
   <details><summary>Answer</summary>The model. Resources are app/user-controlled, prompts are user-controlled, but tool calls are the model's decision based on the conversation.</details>
2. Why can't a stdio server be deployed as an independent cloud service the way a Streamable HTTP server can?
   <details><summary>Answer</summary>stdio requires the host to spawn the server as a local child process and talk over its stdin/stdout — there's no network boundary between them. Streamable HTTP servers are ordinary web services reachable over a URL.</details>
3. What two things does a tool's JSON Schema do?
   <details><summary>Answer</summary>It tells the model what arguments to pass (effectively part of the prompt), and it lets the server validate incoming arguments before running the handler.</details>
